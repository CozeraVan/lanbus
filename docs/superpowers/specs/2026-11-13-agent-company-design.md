# Agent 公司成员网络设计

日期：2026-11-13

## 目标

把 Lanbus 从“host 调用 worker”演进为对称的 agent 网络。每个节点都能发现成员、询问信息、接收消息、派发任务和查询结果。用户安装并配置 MCP 后，只需在任一已加入节点上人工确认加入“公司”，即可与公司内其他成员自由通信。

## 已选架构：去中心化公司能力凭证 + 对称节点 + 本机 MCP

### 公司不是 host

公司只是信任域，不对应某台常在线机器，也不承担消息转发。每个节点保存自己的身份、公司凭证和已知成员目录；通信始终由来源节点直连目标节点。任何现有成员都能审批新成员加入，创始节点离线不影响后续通信或加入。

### 加入即授权

- `company create` 在本机生成随机 `company_id` 和 256 位公司能力凭证，文件权限为仅当前用户可读写。
- 新节点通过 `company join --to PEER --name COMPANY` 发起签名申请。
- 被申请节点显示来源机器、agent、实例标签和公司名，人工批准后返回公司凭证及成员目录。
- 凭证代表整个公司的通信权限，不是逐台 token，也不要求成员两两配对。
- 请求仍使用现有 Ed25519 身份、X25519 会话与 AES-GCM 加密；公司凭证用于成员证明，不能替代消息加密。
- 非成员、错误公司凭证、被移除成员不得执行。审批接口仍只允许 loopback + 本机 approval secret。
- 默认 `request_policy=company`：公司成员自由通信；非公司请求回到原配对流程。可选 `each` 保留每次人工批准；`pair` 保留旧行为。

公司能力凭证采用共享秘密是本次实现的有意取舍：它满足“任一成员可邀请、无中心、加入一次”的要求，但任一成员被攻陷都可能泄露公司凭证。退出公司立即撤销本机凭证；移除其他成员需要目录撤销记录。后续若需要不可抵赖的企业级邀请链，可升级为根证书 + 委派证书，不在本期引入。

## 对称 Agent Node

现有 `PeerServer` 演进为 Agent Node，但保留协议名称以兼容旧版本。节点同时提供：

- 公开发现：节点名、agent 类型、机器名、显示名、实例标签、工作目录、公司 ID 和能力。
- 成员通信：`chat` 与 `project` 使用同一加密请求协议；`project` 只能访问加入时声明并授权的工作目录。
- 任务邮箱：每条请求有 `request_id`，结果可按 ID 查询；等待中的请求在目标离线时报告明确错误，不伪装成功。
- 成员目录：加入和后续通信时合并已知成员元数据，以 `peer_id` 去重；同名实例绝不默认选择第一个。
- 可选通知：新消息和任务可显示桌面通知，但公司成员请求不需要逐次点击。

CLI 的 `worker --direct` 和 `peer` 均成为同一 Agent Node 的兼容启动入口；新文档使用 `lanbus agent`。旧 `worker` 的 Hub 模式保留为兼容功能，不再是直连网络的架构角色。

## 本机 MCP

新增 `lanbus-mcp`（同时支持 `python -m lanbus.mcp_server`）使用 MCP stdio，不暴露无认证的网络 MCP 端口。它通过 loopback + 本机 approval secret 调用 Agent Node，至少提供：

- `lanbus_company_list`：当前公司、成员、在线状态、实例标签和能力。
- `lanbus_agent_discover`：发现局域网节点并返回可区分实例的信息。
- `lanbus_agent_send`：向唯一 `peer_id`／实例标签发送交流请求。
- `lanbus_agent_delegate`：派发项目任务，显式携带工作目录与超时。
- `lanbus_agent_result`：按 `request_id` 查询状态与结果。
- `lanbus_company_join`：发起加入申请；工具只发起，不代替目标机器人工批准。

MCP 配置只写本机启动命令和数据目录，不写公司凭证或 approval secret。secret 由本机数据目录读取。MCP 错误包含重名候选及可操作的实例选择信息。

## 数据流

1. A 的 AI 调用 `lanbus_company_join` 请求加入 B 所在公司。
2. B 的 Lanbus 审批页显示“A 请求加入公司”，B 人工批准。
3. A 获得公司能力凭证和成员目录，A 与 B 保存成员元数据。
4. A 的 AI 调用 `lanbus_agent_send` 给 C；A 直接连接 C，证明公司成员身份并建立加密会话。
5. C 的通知显示“A 发来消息／任务”， executor 直接处理；C 可用相同 MCP 反向询问 A。
6. 严格模式节点可要求逐次批准，此时沿用 request v2 的同密文重发、只执行一次状态机。

## 兼容与错误处理

- 旧版没有公司能力字段时走既有 pair/session/request 协议，不能误判为公司成员。
- 新版与新版已完成 request v2；它仅在 `each` 策略启用。
- 桌面通知失败不丢弃请求；CLI inbox 始终可用。
- 目标离线、超时、拒绝、非成员、重名、目录越权分别返回明确错误。
- 公司凭证不出现在健康接口、日志、通知标题／正文、MCP 配置或 URL。

## 备选方案及取舍

1. **中心公司服务器**：实现简单、目录一致，但重新引入 host 单点，不符合目标，拒绝。
2. **根证书与邀请委派链**：权限证明更强，但证书撤销和链验证显著扩大本期范围，作为后续升级。
3. **共享公司能力凭证**：任一成员可邀请、完全对称、实现面小，采用；明确共享凭证泄露边界。

## 验证

- 三节点 A/B/C：A 经 B 加入后，A↔C、B↔C 均可交流，C 能反向询问 A。
- 只需一次加入审批；公司模式下第二次通信不再产生审批。
- `each` 模式第二次仍需批准，拒绝不执行，相同密文只执行一次。
- 非成员、篡改成员证明、撤销成员、错误公司均不能执行。
- 同机同 agent 多实例通过实例标签寻址，重名错误列出全部候选。
- Python↔Python、Python↔Go 双向及 v1.9.1/v1.9.2 旧版组合。
- MCP `initialize/tools/list/tools/call` 使用真实 stdio 消息验证，不伪造桌面人工审批。
